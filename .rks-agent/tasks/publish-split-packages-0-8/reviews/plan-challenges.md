## Challenge CH-1

- Target claim or boundary: T-001/T-005/T-008 claim that a later rerun of the same merge commit can regenerate and continue with the same byte-identical frozen tarballs after a partial publication.
- Attack: Let the first publish job make core visible, then fail before engine. Rerun the same GitHub commit after `actions/setup-node` resolves a later Node 22 patch or bundled npm release, or after the mutable `ubuntu-latest` image changes. The plan's determinism check compares two packs inside one current environment; it does not bind the packing implementation across runs, and no accepted tarball is retained for the retry.
- Failure mechanism: `dist.integrity` is the SRI of the exact uploaded tarball bytes. A pack-toolchain change can change gzip/tar/manifest bytes without a source change, so the regenerated core identity differs from the already published core. The fail-closed publisher must then reject the retry, while using the regenerated dependents would violate frozen-candidate continuity.
- Task outcome at risk: RQ-011 and RQ-018 require a valid partial 0.8.0 release to be completable from the same frozen candidate, and RQ-017 binds mutation to accepted bytes.
- Credible scenario: The workflow pins only Node major `22`; GitHub runner images and npm bundled with Node are mutable. Partial publication is an explicitly modeled ordinary failure state, and reruns can occur days later.
- Implementation consequence: A conforming implementation can either remain permanently stuck with only core published or relax the identity check and publish siblings from a candidate that is not demonstrably the original frozen set.
- Downstream impact: Consumers see an incomplete immutable 0.8.0 release, or a release set whose common acceptance provenance is broken; neither can be repaired by overwriting npm versions.
- Why now: In-run double generation cannot establish cross-run reproducibility. After the first package exists, discovering that the toolchain cannot recreate the bytes is irreversible and ordinary rollback is unavailable.
- Expected or required behavior: A same-candidate retry must have access to, or reproducibly recreate under a fully bound packing environment, the exact accepted archive set that produced the present package, and must repeat acceptance on those exact unchanged bytes before further mutation.
- Evidence or probe: In a workflow fixture, run candidate generation under two explicitly different supported npm/runner toolchain revisions for the same Git SHA, publish only core from the first identity set, then prove the retry either consumes the retained first set or safely reproduces all three first-set identities. Merely generating twice in one process/image is insufficient.
- Source anchor: Spec Constraints on frozen candidates and same-candidate partial completion; RQ-011, RQ-017, RQ-018; AC-006, AC-012, AC-013; EV-010, EV-011.
- Risk: high-risk
- Minimum mitigation: Bind the exact pack toolchain and provide a durable, non-secret way to recover the original accepted manifest/tarballs for same-run retries, or define an equivalently strong cross-run byte-reproducibility mechanism; re-run complete acceptance after any artifact transfer and before mutation.
- Risk basis: The scenario is a normal modeled partial release, produces either non-completion or identity relaxation, harms an immutable public release, cannot be cheaply repaired after core exists, and needs a plan-level candidate-retention/toolchain decision now.

## Challenge CH-2

- Target claim or boundary: T-004 step 3 claims that per-package `dist.integrity` comparison plus the local frozen manifest can reject every partial state not attributable to the same source/artifact set.
- Attack: Publish core from candidate A, then let a later approved master merge B run while core's projected files and package metadata happen to be unchanged but a missing engine or extensions archive differs. Candidate B's local core tarball can have the same integrity as published core A, while npm has no archive or integrity for the missing sibling to compare.
- Failure mechanism: The plan records source revision and the three identities only in the local candidate manifest. Registry `dist.integrity` identifies each present tarball independently; it does not, by itself, attest the absent siblings or bind the three versions to one joint candidate. No durable cross-package candidate marker or external immutable release record is specified.
- Task outcome at risk: RQ-018 and AC-013 prohibit a later candidate from filling siblings into an earlier candidate's partial release; RQ-017 requires exact accepted-candidate traceability.
- Credible scenario: Core is intentionally stable while adapter or extension packaging changes in a remediation commit. Every later reviewed master push is a release-eligible event under T-005, and a previous run may have stopped after core.
- Implementation consequence: An implementer following only the specified integrity comparisons can accept B as compatible with A and publish B's missing sibling, despite lacking evidence that A's original three-identity set contained that sibling.
- Downstream impact: npm permanently contains a mixed 0.8.0 release assembled from different accepted candidates, defeating the release's joint clean-consumer acceptance and leaving no overwrite rollback.
- Why now: Tests with fixtures can assert a desired answer but cannot derive absent-artifact identity from npm metadata. The attribution data model must exist before any package is published.
- Expected or required behavior: Every present package in a partial state must provide evidence that binds it to the same joint source revision and complete three-artifact identity set proposed for the missing siblings.
- Evidence or probe: Model candidate A and B with identical core tarball identity but different engine identity, expose only A-core Registry metadata, and show what observed field or durable record lets the publisher distinguish A from B without assuming the answer from a fixture label.
- Source anchor: Spec Definitions of frozen release candidate and partial release; RQ-017, RQ-018; AC-006, AC-012, AC-013; EV-010, EV-011.
- Risk: high-risk
- Minimum mitigation: Specify a common candidate identity that is recoverable from each published archive/Registry-visible metadata, or an immutable durable release ledger that records the full accepted identity set before first mutation; require the publisher to compare that joint identity before filling a partial release.
- Risk basis: The causal path uses ordinary stable-core/changed-dependent commits, causes an undetectable mixed immutable release, cannot be corrected later, and requires a minimal shared-attribution mechanism at plan time.

## Challenge CH-3

- Target claim or boundary: T-007/T-008 claim an executable independent-approval and integration sequence, with review evidence in `review.md`, an independently approved PR, and the exact `gh` commands in CK-016.
- Attack: Follow the configured governed workflow literally. Its implementation stage must finish before `change-adversarial` and `final-review`, and its independent complete-result verdict is configured at `reviews/change-review.md`; however T-007, inside the implementation plan, requires approval before its accepted commit and writes a different unconfigured `.rks-agent/tasks/publish-split-packages-0-8/review.md`. Then run CK-016 under the current GitHub identity.
- Failure mechanism: The plan introduces a circular/mismatched approval artifact: the configured final reviewer cannot review the committed complete result until implementation finishes, while implementation cannot finish/commit without a separate review at an unconfigured path. Separately, the current `gh repo view` reports `viewerPermission: READ`, the branch-protection probe returns 404, and collaborator/action-policy probes are forbidden to that identity; therefore push/merge rights and an eligible independent approver are not established for CK-016.
- Task outcome at risk: RQ-009 and AC-011 require current independent complete-result approval before irreversible publication, while the TaskContract requires integration, push, monitoring, and release completion.
- Credible scenario: The controller enforces its declared stage order and artifact paths, or the operator runs the plan's literal `gh` sequence with the currently active account. Both are the observed starting conditions, not hypothetical edge cases.
- Implementation consequence: Execution either deadlocks before the accepted commit, bypasses the configured independent-review gate with an ad hoc artifact, or reaches the end only to fail push/approval/merge after all implementation work.
- Downstream impact: The release is blocked late, or an irreversible publication proceeds on review evidence that the governed controller does not recognize as its complete-result approval.
- Why now: Review ownership/order and repository capabilities define whether the plan is executable. They cannot be safely improvised at the mutation boundary, and late discovery wastes the full implementation/review cycle.
- Expected or required behavior: The plan must use the exact configured review artifacts and a non-circular stage sequence, and must name a demonstrably available write/merge identity plus an independent approver or a source-authorized alternative that preserves independent review.
- Evidence or probe: Reconcile T-007 against `sdd-execution.yaml` artifacts/stage order; then preflight `gh repo view --json viewerPermission`, branch/ruleset requirements, PR review eligibility, and push/merge capability using the identity intended for CK-016 without changing repository state.
- Source anchor: Spec RQ-009, AC-011, EV-007; TaskContract SC-6 and Authorization; configured `sdd-execution.yaml` final-review artifact `./reviews/change-review.md`; Plan BD-007/T-007/T-008.
- Risk: high-risk
- Minimum mitigation: Align T-007 with the controller's `reviews/change-review.md` and post-implementation review/acceptance lifecycle (or explicitly configure a distinct pre-commit review gate without circularity), and add a pre-implementation GitHub capability/independent-approver check with a defined authorized integration identity.
- Risk basis: The currently specified sequence and observed credentials cannot satisfy their own release gate, and bypassing it risks unauthorized irreversible mutation; the smallest correction is stage/path alignment plus an early capability preflight.

## Challenge CH-4

- Target claim or boundary: T-004/T-005 claim that the publish job can query merged-PR approvals and required checks with a read-only token and publish through the repository's trusted CI path, while CK-009/CK-010 are said to validate the workflow.
- Attack: Implement only the permissions and publish behavior explicitly required by the plan. T-005 specifies step-scoped `NODE_AUTH_TOKEN` but does not require `pull-requests: read`, `checks: read`, `contents: read`, or `id-token: write`, and no task or check requires `npm publish <accepted.tgz> --provenance`. The current workflow does have `id-token: write` and `--provenance`, so an otherwise conforming rewrite can silently regress those properties.
- Failure mechanism: With insufficient GitHub token scopes, the approval verifier fails closed after merge and never releases; if implementation weakens the verifier to proceed, it can publish without trustworthy review evidence. Without OIDC permission and the provenance flag, npm accepts token-authenticated archives but publishes them without the existing GitHub provenance attestation. `actionlint` checks syntax, not permission adequacy or npm provenance metadata.
- Task outcome at risk: The approved outcome requires the repository's trusted CI path, reviewed-merge gating, CI-only credential confinement, and traceable accepted-candidate publication (RQ-009, RQ-015, RQ-017).
- Credible scenario: GitHub job permissions are least-privilege and unspecified scopes default to unavailable once a `permissions` block is present. The plan is replacing the existing publish flow and its validations never assert provenance.
- Implementation consequence: A conforming workflow either becomes non-releasing at the final gate or produces irreversible 0.8.0 versions lacking the intended provenance and/or review verification.
- Downstream impact: Delivery is blocked after merge, or public packages lose a supply-chain attestation that cannot be retroactively attached by overwriting version 0.8.0.
- Why now: GitHub permissions and npm publish flags are release-interface requirements, not implementation trivia. Registry mutation is the first point at which the missing provenance becomes observable and too late to repair for that version.
- Expected or required behavior: The release job must have the minimum explicit read scopes needed for commit/PR/review/check queries, retain OIDC provenance permission, use provenance on the exact accepted tarballs, and keep `NPM_TOKEN` limited to the publish step.
- Evidence or probe: A workflow-policy fixture should assert the exact job permissions and accepted-tarball publish argv; a post-release metadata probe should verify npm provenance/attestation for all three versions. Exercise approval API calls under a token with precisely the declared scopes.
- Source anchor: Spec Why and Outcome (trusted CI), RQ-009, RQ-015, RQ-017, EV-004, EV-008, EV-009, EV-010; current `.github/workflows/ci.yml` uses `id-token: write` and `npm publish --provenance`.
- Risk: high-risk
- Minimum mitigation: Add explicit least-privilege GitHub permission requirements (`contents`, `pull-requests`, and checks/status access as used, plus `id-token: write`), require `--provenance` for each accepted `.tgz`, and validate both workflow policy and resulting Registry provenance.
- Risk basis: The omission has two credible outcomes—late fail-closed delivery or irreversible provenance loss—and neither actionlint nor ordinary package smoke catches it before release; a few explicit plan requirements close it.

## Challenge CH-5

- Target claim or boundary: T-009/CK-018 claim that a post-publication local Registry smoke can compare all three `dist.integrity` values with the CI frozen candidate by reading `.release/candidate/manifest.json`.
- Attack: Execute the plan through CI. T-006 explicitly does not commit generated archives, T-005 creates the candidate inside an ephemeral publish job, and no step uploads or otherwise exports the frozen manifest/identity report. After the merge run completes, invoke CK-018 in the local task worktree: its `.release/candidate/manifest.json` is absent, stale, or belongs to the pre-merge branch SHA rather than the merge candidate.
- Failure mechanism: The authoritative identity input to the Registry comparison is destroyed with the runner or confused with a locally regenerated candidate. Logs that merely print identities are not specified as a machine-readable input, and local regeneration reintroduces the cross-run/toolchain problem from CH-1.
- Task outcome at risk: RQ-014 requires real-Registry usability; RQ-017 and RQ-018 require identity traceability to the exact accepted frozen candidate; EV-008/EV-010/EV-011 require the CI/Registry evidence.
- Credible scenario: Ephemeral GitHub runners discard unuploaded files on every successful job, while the plan intentionally excludes `.release/` from commits. CK-018 names only a local relative path and no download step.
- Implementation consequence: The post-release verifier cannot prove published identity equivalence, may compare against the wrong candidate, or is skipped after irreversible publication because its required input is unavailable.
- Downstream impact: An immutable public release can be declared complete without evidence that Registry bytes are the accepted bytes, and later incident diagnosis cannot reconstruct the joint candidate reliably.
- Why now: Candidate evidence must be preserved before the CI job exits. Once discarded, later smoke or ordinary review cannot recreate authoritative release identity cheaply or reliably.
- Expected or required behavior: The exact non-secret frozen manifest and identity report used by the publish job must be durably addressable by merge SHA/run and consumed by the post-release smoke; runtime/type smoke must still install only from the real public Registry.
- Evidence or probe: Complete a no-mutation workflow fixture, delete the runner workspace, and demonstrate the documented command that retrieves the exact manifest by run/merge SHA and supplies it to registry smoke. Verify the retrieved record is cryptographically bound to the accepted tarballs and contains no credential.
- Source anchor: Spec RQ-014, RQ-017, RQ-018; AC-010, AC-012, AC-013; EV-008, EV-010, EV-011; Plan T-005, T-006, T-009 and CK-018.
- Risk: high-risk
- Minimum mitigation: Persist the exact frozen manifest and non-secret identity evidence as a run artifact or equivalently durable immutable record keyed by merge SHA, define its retrieval in T-009, and make CK-018 consume that retrieved CI record rather than an ambient local candidate path.
- Risk basis: The evidence is otherwise predictably lost on runner teardown, undermining exact-byte acceptance after an irreversible release; preservation and retrieval must be designed before publication and are the minimum correction.
